# AI_COLLABORATION

**项目名称：** Ample AI Native OS（ANOS）  
**文档定位：** 多AI协作协议 / 分工 / 交接 / 冲突处理  
**适用对象：** Codex、Claude、ChatGPT、后续AI助手与人类负责人  
**版本：** V1.0  
**状态：** 协作基线

---

## 1. 协作目标

多AI协作的目标不是让多个AI重复生成内容，而是形成清晰分工：

```text
ChatGPT / Claude
负责理解、分析、架构、文档草案

Codex
负责工程落地、文件修改、测试验证

人类
负责业务确认、敏感规则和最终验收
```

所有AI必须围绕同一套项目事实工作，避免各自发明一套ANOS。

## 2. 项目入口

新AI进入项目时，应按渐进式披露顺序阅读：

1. `instructions.md`
2. `AGENTS.md`
3. `docs/CONTEXT.md`
4. 与当前任务直接相关的专项文档

不要一开始读取所有文档，除非任务需要全局审查。

## 3. 角色分工

## ChatGPT

适合：

- 产品讨论。
- 业务推演。
- 管理层表达。
- 架构方向比较。
- 大段对话沉淀为文档草案。

不适合：

- 直接修改本地仓库文件。
- 未经确认执行生产操作。

## Claude

适合：

- 长文档阅读。
- 需求分析。
- 文档冲突审查。
- 架构评审。
- 章节级重构建议。

输出应便于Codex直接落文件。

## Codex

适合：

- 修改仓库文件。
- 建立目录结构。
- 编写代码、脚本、测试。
- 运行校验。
- 把确认后的方案落地。

Codex必须保护已有修改，不得覆盖未理解的用户或其他AI变更。

## 人类

负责：

- 定方向。
- 定边界。
- 定优先级。
- 定敏感规则。
- 定上线与验收。

## 4. 标准交接格式

AI之间交接应包含：

```text
任务目标：

已读文档：

已完成内容：

关键结论：

待确认事项：

建议下一步：

风险：
```

如果交接给Codex，还应补充：

```text
待修改文件：
新增文件：
验证方式：
验收标准：
```

## 5. 冲突处理

冲突类型：

- 文档结论冲突。
- 字段命名冲突。
- 权限边界冲突。
- MVP范围冲突。
- AI建议与人类确认冲突。

处理规则：

1. 不直接覆盖。
2. 标注冲突位置。
3. 给出影响分析。
4. 交由人类确认。

优先级：

```text
人类最新确认
↓
MVP定义
↓
白皮书
↓
专项文档
↓
AI推论
```

## 6. 文档协作规则

新增正式文档时：

- 使用编号。
- 保持中文。
- 保留元信息。
- 明确上游文档。
- 明确状态。
- 标注待确认事项。

修改正式文档时：

- 不做无关重写。
- 不改变已确认结论。
- 新增内容应与目录和上下文一致。

## 7. 工程协作规则

工程开发前必须确认：

- MVP范围。
- 数据模型。
- 权限边界。
- 测试方式。
- 是否涉及真实外部系统。

涉及真实飞书、ERP、金蝶写入前，必须获得人类明确授权。

## 8. 状态标记

建议所有重要交付标记状态：

- Draft：草案。
- Review：待审。
- Baseline：基线。
- Implementing：实施中。
- Deprecated：废弃。

当前大部分P0文档状态为实施准备基线，不等于真实业务规则全部最终确认。

## 9. 防重复机制

新AI开始前必须先查：

- 是否已有同名文档。
- 是否已有相近编号文档。
- 是否已有上游定义。
- 是否应修改旧文档而非新增文档。

如果只是实施细化，应优先补充已有文档；如果形成新责任边界，才新增文档。
